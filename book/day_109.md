## 2. The Architecture (Why)

### Phase 1 -- the construction-level proof

Day 108 attempt 1 failed at Cloud Run deploy step 07 with:

    Permission denied on secret: projects/195673983724/secrets/
    internal-api-key/versions/latest for Revision service account
    195673983724-compute@developer.gserviceaccount.com.

Day 108's Cloud Shell `add-iam-policy-binding` returned the truth:

    Secret [projects/195673983724/secrets/internal-api-key] not found.

Two messages, same meaning. GCP returns "Permission denied" for
nonexistent secrets -- a security-through-obscurity choice. The
diagnostic path that reads the message literally assumes an IAM problem
and wastes a deploy cycle. The path that tries the Cloud Shell command
first learns the actual state.

**The construction-level proof:** gcloud validates `--set-secrets` at
deploy time. If `internal-api-key` did not exist, or the SA could not
read it, the deploy would fail identically. Deploy attempt 2 succeeded,
therefore the secret exists and the SA can read it. **We cannot directly
observe the env var from outside** (would need Cloud Run log access which
requires gcloud auth in Colab, or a call to a callback that echoes its
own env). But the deploy success IS the proof -- stronger than an
external observation, because it is exactly the operation we care about
succeeding.

### Phase 2 -- design decisions, honestly audited

**Decision 1 -- where does "My Essays" live?**

Three options: (a) new route `/essays` (chosen), (b) section within
`/dashboard`, (c) modal from `/studio`.

**A. Route `/essays`** -- chosen. Why: the component is a full page
(list + expand + pagination), the URL is shareable/bookmarkable, the
Navbar entry is discoverable, and it matches the existing pattern (every
major feature is a route). Dashboard-integration (b) would compress the
list into a card, hiding pagination and the expand interaction. Modal
(c) would hide essays behind a /studio page a user only visits when
actively writing -- the wrong affordance for reviewing past work.

**Decision 2 -- new `essaysAPI` export, not new method on `writingAPI`**

`api.js` already had a `writingAPI` object with a mocked `submitPractice`
(Cell 17 finding). Two paths: extend `writingAPI` with a `listEssays`
method, or add a new `essaysAPI` export.

**Chosen: new export.** Reasons:
- `writingAPI.submitPractice` is a mock (`console.warn` + fake return).
  It represents a *plan* that was not fulfilled. Adding real methods
  next to a mock sends the wrong signal.
- Appending a new export at end-of-file is unambiguous (no brace-matching
  transform needed). This matters: two Cell 18a attempts failed on a
  brace-region transform; exact-string append is the pattern that worked.
- Cost: 14 lines of near-duplicate structure (both use the same axios
  instance). Accepted for clarity of intent.

`writingAPI` is preserved untouched (Rule Zero).

**Decision 3 -- server-side tenant isolation**

The list endpoint uses `WritingFeedback.objects.filter(user=request.user)`
-- never `request.user_id` from the body, never a query param. Tenant
isolation is not a UI concern that can be bypassed by an adversary with
DevTools. It is a server-side invariant tested with an explicit
cross-user call (Cell 18b-2 test B: `student_basic` sees 0 rows).

**Decision 4 -- `page_size` capped at 100**

The query parser clamps `page_size = max(1, min(page_size, 100))`.
Without the cap, a user with 10,000 essays could `?page_size=99999` and
receive all of them in one response -- a self-DoS at best, a
full-table-exposure surface at worst. The cap is 100 (a small multiple
of the default 20), verified in Cell 18b-2 test E.

**Decision 5 -- serializer is read-only**

`WritingFeedbackSerializer` sets `read_only_fields = fields`. The
endpoint has no write path today; the serializer is scoped to the list
use case only. If a future endpoint needs to update a row (e.g., mark
as reviewed), a separate serializer would be added -- not a widened
`Meta.fields` with conditional read-only. Widening is how "read-only
serializer accidentally accepts client writes" bugs happen.

This is the first day in the project's history where all three lenses

### What this is NOT

- **Not production persistence end-to-end.** The UI works against
  Cloud Run for *auth and Claude calls*, but the background task that
  would POST new feedback to Django still hits loopback
  (`DJANGO_API_URL=http://127.0.0.1:1/disabled`). New essays submitted
  from `/studio` in production today will:
    - Return feedback to the browser (WORKS)
    - Fire a background task that fails on loopback (LOGGED, NOT PERSISTED)
    - Not appear in "My Essays" (because no row was created)
  The 3 rows visible in the browser today were seeded directly via ORM
  (Cell 18b-2). Closing this gap is Day 110's primary: point
  `DJANGO_API_URL` at a reachable Django URL.
- **Not tier auto-unlock.** Day 106 finding 1 (`update_progress()` sets
  `is_completed` but never flips `is_unlocked` on the next tier) remains
  open. Deferred to Day 110.
- **Not a UI iteration.** The component is functional and honest but not
  polished. Loading states, empty states, error states are present and
  minimal. Design-polish is Phase 2 Days 112-114.

## 4. The Debugging Diary (Exact errors and fixes)

**Three entries. Two system bugs (same family). All caught before
corruption by ast.parse-before-write.**

### Entry 1 -- prepending to a closing paren produced WritingFeedback,)

- Cell 18a: to add WritingFeedback to imports of serializers.py, I
  found the closing paren line of a multi-line import and did
  lines[close_idx] = "    WritingFeedback," + lines[close_idx]. When
  the line was just ), the result was "    WritingFeedback,)" -- name
  and paren on same line, no separator.
- ast.parse before write caught it. serializers.py intact at 687 lines.
- Lesson: concatenating around a delimiter that may be a newline or a
  paren is fragile. The transform must be insertion, not concatenation.

### Entry 2 -- inserting a line before an uncommaed item

- Cell 18a-fix: changed to lines.insert(close_idx, "    WritingFeedback,").
  Now the new line was on its own, before ). But the line above
  (PracticeSession, TestSession) had no trailing comma -- so Python saw
  two names on consecutive lines inside parens with no separator.
  Syntax error at line 12.
- ast.parse before write caught it. File intact.
- Lesson: the line above the closing paren may or may not end with a
  comma. A general transform must inspect it. Better: exact-string
  replacement.

### Entry 3 -- exact-string replacement worked (third try)

- Cell 18a-fix2: OLD = "    PracticeSession, TestSession\n)",
  NEW = "    PracticeSession, TestSession, WritingFeedback\n)",
  assert OLD in txt, then txt.replace(OLD, NEW, 1). Assertion passed,
  replacement applied once, both isolated import block and whole file
  parsed, file written, smoke test created a temp row, serialized with
  all 11 fields, cleaned up.
- Lesson: when a transform fails twice, switch to exact-string
  replacement. It is unambiguous, verifiable, fails loudly if the file
  differs. The assert OLD in txt makes it safe.

### Entry 4 -- chapter paste truncation from code fences

- Cells 22b and 22b-1 attempted to append markdown content that
  contained triple-backtick bash code fences. Both pastes truncated at
  the start of the content string (IncompleteInputError at the opening
  triple-quote). The code fences inside the Python string were the
  likely trigger.
- Fix: cells 22b-1a and 22b-1b removed code fences entirely (used
  4-space indented code blocks instead -- same markdown rendering, no
  backticks), reduced content per cell to ~70 lines, added
  COPY START / COPY END markers around the payload, and used a
  single-line Path.write_text() instead of a with block.
- Lesson: paste reliability degrades with content size and with
  embedded delimiter sequences. Split into small cells, avoid
  delimiters inside the payload string, mark copy boundaries
  explicitly.

### Entry 5 -- substring asserts on common words

- Cell 22b-1a asserted "### Phase 2" not in new, intending to check
  that Phase 2 had not yet been written. But Part 1 (section 2) already
  contained "### Phase 2 -- design decisions, honestly audited" --
  guaranteed to match regardless of what Cell 22b-1a added. The
  assertion failed spuriously after a successful write.
- Fix: cells 22b-1b onward use unique-phrase asserts -- the full text of
  the specific content that cell is responsible for, never a common
  prefix.
- Lesson: assert on the exact phrase that proves the specific work
  landed, not on a shared prefix or keyword. Substring asserts on
  common words pass when unrelated content is present, and fail when
  the file actually contains the correct new content -- both directions
  wrong.

### Meta-lesson -- ast.parse-before-write is what makes exploratory transforms safe

Three Cell 18a attempts, all failures caught by ast.parse before write.
Zero bytes lost, zero corruption. Without ast.parse-before-write, entry
1 would have written a broken serializers.py, and entries 2 and 3 would
have run against an already-broken file. The debugging path becomes
"which of three overlapping bugs am I looking at?". The verify-before-write
discipline is the invariant that makes every transform attempt safe
regardless of how many attempts it takes.

## 5. Key Takeaways

**5.1 -- Give the user-visible deliverable a day.** "My Essays" was the
Day-N+1 task on Day 107 and Day 108. It shipped today because Day 109
was structured as Phase 1 (10 min fix) then Phase 2 (90 min build) and
Phase 2 was protected. Days 107 and 108 both had real work in their
block; the visible thing lost out because no cell said "this is the
block." The lesson is structural, not motivational.

**5.2 -- Construction-level proof is stronger than observational proof.**
The INTERNAL_API_KEY env var is proven set because the deploy
succeeded; gcloud validates --set-secrets at deploy time. We never
directly observed the env var on the running container -- we proved it
by the operation that depends on it. This is the correct answer to
"how do you know X is true?" when X is an invariant of a deploy, not
a fact about a runtime.

**5.3 -- Bundle-hash-as-proof is the frontend ast.parse.** A component
file can be created but never imported; tree-shaking removes it; the
build succeeds; the app does not use it. Asserting the hash changed
after each edit is a syntactic proof that the edit reached the bundle.
Cheaper and more reliable than open the browser and see if it works.

**5.4 -- 5 sub-tests in one cell, not 5 cells.** Same pattern as Day 107's
Cell 6b-3. The rule is "one concern per cell", not "one assert per
cell". Five tests of "does this endpoint behave correctly" is one
concern. Failure messages from each already distinguish the layer, so
the cell does not need to isolate further.

**5.5 -- Exact-string replacement when a transform fails twice.** Three
attempts to add an import. The first two used transforms; the third
used exact-string replacement with assert OLD in txt. Transforms are
powerful and fail modes are subtle. Exact-string replacement is simple,
verifiable, fails loudly. When you find yourself on attempt three,
switch strategies -- do not attempt a third transform.

**5.6 -- Paste reliability degrades with size and embedded delimiters.**
Cells 22b and 22b-1 both truncated on content containing triple-backtick
code fences inside a Python string. Cells 22b-1a onward work reliably
with: <=100 lines per cell, no code fences in the payload, COPY START /
COPY END markers, and a single-line Path.write_text() (no indented
with block). This is the delivery mechanism we will use for book
chapters from Day 110 onward.

**5.7 -- Assert on unique phrases, never common words.** Substring
asserts on keywords like "### Phase 2" match unrelated content and
fail when the actual new content is correct. The correct assert is on
the exact phrase the cell is responsible for producing. This cost one
turn on Day 109; the fix is one line per assert.

**5.8 -- What remains for Day 110.** Four items, ranked:

1. DJANGO_API_URL -> stable tunnel URL. Closes end-to-end persistence
   in production. New essays from /studio will persist and appear in
   "My Essays." Requires per-session redeploy, or a named cloudflared
   tunnel with a stable subdomain.
2. TierProgress.update_progress() auto-unlock. Day 106 finding 1.
   15 lines + a test.
3. fastapi.log append mode. Day 107 defect. One-line fix.
4. UI polish for My Essays. Loading spinner, error copy, empty-state
   illustration. Deferred to Phase 2 Days 112-114.
