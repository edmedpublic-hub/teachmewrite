## 2. The Architecture (Why)

### Why stopping here is correct

The alternative was to push through: create the secret, grant IAM,
rerun deploy, verify persistence, then start "My Essays" UI. That was
the wrong move:

  - Deploy + IAM debugging is 20+ minutes minimum in a fresh attempt
  - Every subsequent cell would build on a tired foundation
  - The current state is clean: no half-deployed revision, no silent
    failures, no uncommitted edits
  - The pending task is 3 commands from a fresh session, zero risk

A senior engineer stops at clean stopping points, not at "I can see the
end." Today the end is visible, which is precisely why the discipline
matters: the temptation to push through the last 20 minutes is the
temptation that produces mistakes in the 20 minutes that follow.

### Three-lens audit

**Seamless:** The live service is binary: fully working or fail-closed.
Never "half-working." Today's deploy failure moved the callback from
"auth fails-closed" to a state where auth could pass but the deploy
itself failed -- but did not create a middle ground where some requests
silently succeed. The user either gets feedback (works) or an error
(honest), never lost data.

**Easy UX:** No user-visible change today. This is the second consecutive
day with no visible deliverable. The chapter must be honest that "My
Essays" UI was deferred again, and that Day 109 must deliver it or the
persistence work remains invisible to the student.

**Futuristic:** We discovered two additional layers of infrastructure
that will apply to *every future capability*: workflow paths filters
(which files trigger a deploy) and per-secret IAM bindings (which
service accounts read which secrets). Naming these layers today makes
every future capability -- new secret, new workflow, new service --
faster to add. That is the futuristic artifact of Day 108.

### The two layers, named

**Layer 1 -- Workflow paths filter.** `on.push.paths: ['ai-service/**']`
means a `deploy.yml` edit does not trigger the workflow that uses
`deploy.yml`. The workflow could not validate its own definition file
changes. This is a general pattern: workflows should trigger on their
own definition files, not just on files they operate on.
Fix: add `.github/workflows/**` to the filter. Done: commit `0c5305b`.

**Layer 2 -- Per-secret IAM bindings.** A service account that can read
secret A cannot automatically read secret B. Each secret needs its own
`roles/secretmanager.secretAccessor` binding to the specific service
account that will read it. This is not "set up once, works forever."
Fix: one `gcloud secrets add-iam-policy-binding` call per new secret.
Not done yet: pending Day 109.

### The GCP API quirk that cost 40 minutes

When a Cloud Run deploy references a secret that does not exist, the
deploy error reads:

    Permission denied on secret: projects/PROJECT/secrets/NAME/versions/latest
    for Revision service account SA_EMAIL.
    The service account used must be granted the Secret Manager Secret
    Accessor role...

That language ("Permission denied") suggests an IAM problem. It is not.
For a nonexistent secret, GCP returns "Permission denied" to obscure
existence -- a security-through-obscurity design choice. The Cloud Shell
`add-iam-policy-binding` call returned the truth:

    Secret [projects/PROJECT/secrets/NAME] not found.

Both messages mean the same thing: the deploy cannot attach this secret
to the revision. The fix is identical either way (create the secret,
add a version, bind IAM). But the diagnostic path that assumed "IAM
issue, grant permission" wastes a deploy cycle (5-6 minutes) before the
real cause surfaces. Reading the Cloud Shell result first would have
saved that cycle.

## 3. The Implementation (How)

### Two commits, both in `deploy.yml`

**Commit `9a3a320`** -- one line changed:
`--set-secrets ANTHROPIC_API_KEY=anthropic-api-key:latest`
became
`--set-secrets "ANTHROPIC_API_KEY=anthropic-api-key:latest,INTERNAL_API_KEY=internal-api-key:latest"`

The quotes were added because the value now contains a comma. Without
quotes, gcloud would treat `INTERNAL_API_KEY=internal-api-key:latest`
as a shell argument instead of part of the --set-secrets value.

**Commit `0c5305b`** -- one line changed:
`paths: ['ai-service/**']` became
`paths: ['ai-service/**', '.github/workflows/**']`

This commit is self-proving: it changes `deploy.yml`, and the new filter
matches `.github/workflows/**`, so the workflow triggers itself.

services. All of Day 108's code work was in deployment configuration.
That is why the resume cells were necessary: today's work is *about

## 4. The Debugging Diary (Exact errors and fixes)

**Nine entries. Two are system bugs, seven are test-harness or
process. The ratio reversed from Day 107 but the class is the same.**

### Entry 1 -- `.env` did not survive the session

- Resume Cells 1-12 ran fine, then Cell 13a failed with
  `AssertionError: Missing: /content/teachmewrite/backend/.env`.
- Cause: Day 107's `.env` was written to Colab's ephemeral disk and
  gitignored. Fresh session, fresh clone, no `.env`.
- Fix: Cell 13b generated a fresh key, wrote `.env`, and Cell 13c-fix
  added a **second persistence layer**: `/content/drive/MyDrive/teachmewrite-ai/.secrets/internal_api_key`.
  Drive survives sessions. Fingerprint `2c4be7f1` verified.
- Lesson: **secrets in `.env` on ephemeral storage do not survive
  sessions. Persistence requires Drive, Secret Manager, or a proper
  vault.** Two layers minimum for local dev.

### Entry 2 -- Key accidentally pasted into chat

- Cell 13b printed the generated key in the notebook. I pasted that
  output block back to the assistant -- the key entered the chat
  transcript.
- Fix: Cell 13b-rotate generated a new key silently (length only, no
  value printed in conditional output). The exposed key is dead.
- Lesson: **assistant messages must not require the user to paste
  secret values back. If they must, the user must be warned explicitly
  and the cell must not include the value in its own output.**

### Entry 3 -- `gcloud auth login` in Colab fails with EOFError

- Cell 13i-a ran `gcloud auth login` inside `subprocess.run()`. gcloud
  printed the OAuth URL, prompted for verification code, and got
  `EOFError: EOF when reading a line` -- no TTY on stdin in Colab.
- Fix: pivoted to Cloud Shell (browser-based, pre-authenticated). One
  command in the browser, no auth dance.
- Lesson: **interactive CLI tools in Colab need TTY plumbing. For one-off
  auth, Cloud Shell is faster than plumbing.**

### Entry 4 -- GCP "Permission denied" for a nonexistent secret

- Deploy step 07 failed with `Permission denied on secret:
  projects/195673983724/secrets/internal-api-key/versions/latest for
  Revision service account 195673983724-compute@developer.gserviceaccount.com`.
- Diagnosis path assumed IAM issue -- tried to grant
  `secretAccessor` via Cloud Shell.
- Cloud Shell `add-iam-policy-binding` returned the truth:
  `Secret [projects/195673983724/secrets/internal-api-key] not found`.
- Cause: STEP B of the migration instructions (create the secret) was
  never completed. GCP returns "Permission denied" for nonexistent
  secrets, not "Not found" -- security-through-obscurity.
- Fix (Day 109): `gcloud secrets create internal-api-key` with
  `--data-file=-` piped from the actual key value, THEN
  `add-iam-policy-binding`.
- Lesson: **GCP "Permission denied" is not always permission. Try the
  Cloud Shell command first -- it tells you whether the resource exists
  before you chase IAM.**

### Entry 5 -- Premature "COMPLETE" footer in Cell 13g

- Cell 13g's footer printed `[summary] DEPLOY SUCCEEDED ...` in a
  conditional branch, then unconditionally printed
  `[cell13g] Day 108 primary #1 is COMPLETE.` regardless of outcome.
- When deploy failed, both messages appeared -- contradictory.
- Fix: Cell 13i's footer puts DONE inside the success branch. But this
  is the same bug class as Day 107 entry 3 (`pre_count = 0` assignment,
  not assertion). A footer after a conditional is a lie if the
  conditional is not enforced with `assert` or `raise`.
- Lesson: **never print DONE after a conditional that could fail. Use
  `assert outcome == expected` before DONE. If you cannot assert,
  print the outcome state, not a completion claim.**

### Entry 6 -- Premature "if rc=0 proceed" in Cell 13i-a

- Cell 13i-a printed `[cell13i-a] DONE -- if rc=0, proceed to Cell 13i-b`
  regardless of `r.returncode`.
- User refused to proceed when gcloud failed -- correct behavior, but
  my cell implied it was fine to move on.
- Fix: same as Entry 5, use `assert r.returncode == 0` before DONE.
- Lesson: **conditional DONE without assert is a footgun. Three times
  in one week (Day 107 entry 3, Day 108 entries 5 and 6). From now on,
  every cell footer DONE is preceded by an `assert`.**

### Entry 7 -- DNS backoff earned its keep

- Cell 11's cloudflared tunnel took 4 failed DNS attempts before
  resolving on attempt 5 (18s cumulative wait).
- Without Day 107's backoff lesson, this would have been a false
  negative requiring manual retry.
- Fix: none needed -- the Day 107 lesson prevented the bug.
- Lesson (positive): **the Day 107 discipline worked. First cell of the
  week where a prior lesson prevented an actual bug.**

### Entry 8 -- `SystemExit` in Jupyter cells

- Cell 13e's diagnostic branch called `raise SystemExit(0)` to exit
  cleanly. Jupyter intercepts SystemExit and prints a traceback +
  warning. The cell exited correctly but the output was noisy.
- Fix: cells should end naturally instead of raising. If early exit is
  needed, `return` is not available at cell top-level; use a conditional
  wrap of the entire remaining body.
- Lesson: **`SystemExit` works but is noisy in Jupyter. Prefer nested
  `if` over `raise SystemExit` for early exit in notebook cells.**

### Entry 9 -- Job logs endpoint returns text, not zip

- Cell 13h asserted the response body starts with `PK` (zip magic bytes).
  It started with `\xef\xbb\xbf` (UTF-8 BOM) -- the endpoint returns
  plain text for completed jobs.
- Cause: `/repos/{owner}/{repo}/actions/jobs/{job_id}/logs` returns text.
  `/repos/{owner}/{repo}/actions/runs/{run_id}/logs` returns zip. I
  used the wrong endpoint for the wrong assumption.
- Fix: Cell 13h-2 decoded as text, grepped, and printed the tail.
- Lesson: **GitHub Actions has two log-download endpoints with
  different return formats. Job logs = text. Run logs = zip.**

## 5. Key Takeaways

**5.1 -- Two infrastructure layers invisible until needed.** Workflow
paths filters determine what triggers a deploy. Per-secret IAM bindings
determine who can read each secret. Neither is visible in the codebase.
Both must be right for "git push triggers deploy" to work. Naming them
today makes every future secret and every future workflow faster to add.

**5.2 -- Clean stopping points are a discipline, not a luxury.** The
alternative was to push through: create secret, grant IAM, rerun deploy,
verify persistence, start "My Essays" UI. Twenty minutes minimum more.
But those twenty minutes would have been on a tired foundation, and the
marginal hours produce the marginal mistakes. **The end being visible is
exactly when to stop** -- not the opposite. Stopping at clean boundaries
is the discipline that makes tomorrow start well.

**5.3 -- The process files are the memory across sessions.** README.md,
ARCHITECTURE.md, TRANSITION_PROMPT.md were started around Day 100 and
left to drift. Today we noticed the cost: assistant memory does not
persist, but files do. Restoring these at day-end is not ceremony -- it
is the mechanism by which a session-to-session project maintains
coherence. Day 109 opens with them current.

**5.4 -- One concern per cell, even when the next three are visible.**
Today drifted toward grouped cells in 13c-fix through 13g, reasoning
that "these are one concern." They were not: diagnosis, decision, and
edit are three concerns. When the first step failed, the subsequent
two steps were wasted. The user's observation was correct and is now
Day 109's default: one concern per cell.

**5.5 -- Conditional DONE without assert is a footgun. Three times in
one week.** The pattern is: `if condition: do_work()` followed by
unconditional `print("DONE")`. Fix: `assert condition` before DONE, or
move DONE inside the `if` branch with an `else` that prints the actual
state. The rule is not "be careful with footers." The rule is "**every
DONE is preceded by an `assert` that would raise if the state were
wrong.**" Failures in the footer are the failures that produce false
confidence.

**5.6 -- The user is the last line of defense.** Twice today (Cell 13i-a's
footer, and the paste-back of the key), the user caught a problem that
my cells introduced. This is not a failure of the cells alone -- it is
the working relationship functioning correctly. Good cells catch their
own bugs; good process catches the cells that do not.
