## 1. The Milestone

Day 111 set out to retire the per-session `deploy.yml` edit. The tunnel URL
rotated every session, the deploy therefore had to be edited and redeployed
every session, and the loop could not be relied on. A named cloudflared tunnel
at `api.teachmewrite.com` removed the rotation. That work landed on Day 111 as
`83e25e0`, but the deploy that should have proven it failed its golden-set gate
with `0/20 HTTP 502`, and the failure persisted across Days 112 and 113.

On Day 113 the gate passed 20/20 and the deploy promoted the new revision to
100% traffic. Three separate failures stood between Day 111's commit and this
result, and each was diagnosed and fixed on its own terms:

1. **The Cloud Run container's Anthropic key was stale.** The `invalid x-api-key`
   error appeared in the container log, and the ai-service mapped that to 502 on
   every `/feedback` request. Fixed by updating the Secret Manager secret and
   creating a new revision (`00101-kif`) that reads `anthropic-api-key:latest`.
2. **The gate's judge was using a different, also-stale key.** The judge runs in
   the GitHub Actions runner and reads `secrets.ANTHROPIC_API_KEY`, not Secret
   Manager. The container was fixed while the judge was still failing with
   `judge exception: Error code: 401 - invalid x-api-key`. Fixed by updating the
   GitHub Actions repository secret to the same new key.
3. **Golden-set case `g13` was correctly failing on a real scoring regression.**
   The model scored a grammar-correct, redundancy-only sentence at 72, inside
   the 70-80 band the prompt reserved for near-empty text like "Hello." The
   case's own `_note` says v3 intends 80-95 for this class: flag clarity, do not
   drop the score. Fixed by disambiguating rule 3 in the prompt (`1d9a2e1`).

Each fix was its own commit. The gate passed only when all three were in place.

## 2. The Architecture (Why)

### Three stores, three failures

The same key exists in three places, and each was updated independently:

- **Colab Secrets** -- the notebook's copy, used by local probes and by the
  bootstrap cell. Not read by Cloud Run, not read by the gate.
- **GCP Secret Manager** -- `anthropic-api-key:latest`, read by the Cloud Run
  container at revision startup. Not read by the gate.
- **GitHub Actions repository secret** -- read by the gate step's `env` block in
  `deploy.yml`, used by `run_gate.py`'s judge. Not read by Cloud Run.

Rotating the Anthropic key in the console invalidates the old key everywhere at
once, but updating one store does not update the others. The correct order is:
rotate in the Anthropic console, update Secret Manager, update the GitHub
secret, redeploy. Day 113 fixed them one at a time because the failures surfaced
one at a time; the lesson for the future is that the rotation is a three-store
operation and the bootstrap should say so.

### Why the prompt fix is a code fix, not a test fix

Golden-set cases are authored expectations. When a case fails, the temptation is
to widen the expected range until the model passes. That is wrong when the case
is catching a real regression, and it is the one thing a quality gate must not
do. The discipline is to read the case's own `_note` and decide whether the
expectation or the model is wrong:

- `g13`'s `_note` records the v3 policy explicitly: "error-anchored scoring
  gives grammar-correct text 80-95. Redundancy must still be FLAGGED as clarity,
  but does not drop the score."
- The model scored 72. The score band is `[75,95]`. The model was not following
  its own written policy.
- The prompt had two rules that could apply to a short, correct, redundant
  sentence -- rule 3's zero-errors band (80-95) and rule 3's "extremely short
  but correct" band (70-80) -- and did not say which wins. The model chose the
  near-empty band.
- The fix was to say what the near-empty band does *not* cover: a short but
  substantive sentence with zero grammar errors stays in 80-95 even if it is
  redundant.

The golden set is unchanged. `run_gate.py` is unchanged. The case was right; the
model was wrong; the prompt was ambiguous. Fixing the prompt is the honest fix.

### The aggregate exit rule

`run_gate.py` line 143 exits 1 unless `passed == len(results)`. That is
all-or-nothing per case. A 19/20 result is a failure, not a pass. That is the
correct rule for a gate whose purpose is to catch regressions -- a gate that
tolerates one bad case cannot catch the one bad case that matters. The `g13`
failure was not tolerated; it was fixed at the source.

## 4. The Debugging Diary

### Entry 1 -- 502 from Cloud Run, cause was the Anthropic key, not the origin

The gate reported `0/20 HTTP 502`. Day 111's chapter attributed a similar
signature to the Colab origin being down at gate time. That diagnosis was wrong
for this failure, and the request logs alone could not distinguish them. The
container log for revision `00099-pag` showed:

    Anthropic API Error: Error code: 401 -
    {'type': 'error', 'error': {'type': 'authentication_error',
     'message': 'invalid x-api-key'}}

The handler caught the 401 and returned 502. Every `/feedback` failed at the
Anthropic call, before the callback to Django could fire. `django.log` had no
lines from the gate window, which was the tell: if the failure had been the
origin being down, the callback would have fired and the log would show it.

Lesson: **a 502 from a service is not a statement about the service's
upstream.** Read the container log, not the request log, and look for the
component that actually returned the error.

### Entry 2 -- container fixed, gate still failed, because the gate's key is a different key

After the Secret Manager update and the new revision `00101-kif`, the container
log showed `POST /feedback HTTP/1.1 200 OK` on every gate request. The container
was healthy. The gate still failed 0/20, with:

    judge exception: Error code: 401 - invalid x-api-key

The judge runs inside the GitHub Actions runner, not inside the container. It
reads `secrets.ANTHROPIC_API_KEY` from the repository. The repository secret was
still the revoked key. Updating the container's store did not touch the gate's
store.

Lesson: **a rotated key lives in more than one store.** Secret Manager feeds
Cloud Run; GitHub Actions secrets feed the workflow. Updating one is not
updating the other, and "the container is healthy" does not mean "the gate can
authenticate."

### Entry 3 -- the gate failed on a real regression, and the right fix was the prompt

With the key fixed, 19/20 passed and `g13` failed with `score 72 outside
[75,95]`. The case's `_note` says v3 intends 80-95 for grammar-correct redundant
text. The prompt's rule 3 had two bands that could apply and did not say which
won, so the model picked the 70-80 near-empty band. The fix scoped the
near-empty band to word-or-phrase texts and added an explicit rule that a short
substantive sentence stays in 80-95. The gate then passed 20/20.

Lesson: **a failing golden-set case is not always a flaky expectation.** Read the
case's `_note` before touching the range. If the model violates its own written
policy, fix the prompt, not the test.

### Entry 4 -- the aggregate exit rule is all-or-nothing, and that is correct

`run_gate.py` exits 1 unless every case passes. A 19/20 result is a failure.
That is the right rule for a regression gate. The temptation to loosen it to
"tolerate one failure" was rejected because a gate that tolerates one bad case
cannot catch the one bad case that matters.

## 5. Key Takeaways

**5.1 -- One milestone can take three days of infrastructure and one prompt
fix.** The stable URL landed on Day 111 and shipped on Day 113. The delay was
not waste; it was three independent failures discovered in the order they
blocked the gate. Each was fixed as its own commit.

**5.2 -- A 502 is a symptom, not a cause.** Cloud Run's 502 can mean the
container crashed, the origin is down, or the handler returned a 5xx. The
container log names the cause; the request log does not. Read the container log
first.

**5.3 -- A rotated key is a multi-store operation.** Anthropic console, Secret
Manager, GitHub Actions secrets. Three stores, three updates, and the deploy is
the event that forces all three to agree. The bootstrap in `RULES.md` should
name all three.

**5.4 -- A golden-set failure is a question, not a verdict.** Read the case's
`_note`. If the expectation is right and the model is wrong, fix the prompt. If
the expectation is wrong, fix the case. Do not widen the range to make the red
go away; that is how a quality gate stops being one.

**5.5 -- All-or-nothing gate exit is the correct default.** Tolerance for one
failure is tolerance for the one that matters. Fix the source.
