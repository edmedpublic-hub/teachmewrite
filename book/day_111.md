## 2. The Architecture (Why)

### Named tunnel vs. quick tunnel vs. Django-on-Cloud-Run

Day 110's `trycloudflare.com` URL is a **quick tunnel**: free, anonymous, and
ephemeral by design. The URL is assigned per process, and Cloudflare makes no
guarantee it survives a restart. That is the right tool for a 60-minute
prototype, and the wrong tool for a URL that a production service depends on.

Day 111's `api.teachmewrite.com` is a **named tunnel**: the tunnel has an
identity (UUID), the DNS CNAME points at that identity (not at a URL), and the
credentials on disk let any `cloudflared` process reconstruct the tunnel. The
UUID does not change across restarts, so the CNAME does not change, so
`DJANGO_API_URL` does not change. The origin behind the tunnel -- the Colab
runserver -- is ephemeral, but the **address** is stable. That is the difference
that matters: Cloud Run's `BackgroundTask` and the deploy pipeline's golden-set
harness both need a hostname that does not rotate.

The third option -- Django on Cloud Run -- was considered and rejected on Day
111 for the same reason Day 110 rejected it: it forces Postgres, Secret Manager,
a Dockerfile, and a new deploy pipeline, all of which are Phase 3 work. Named
tunnel is the smallest change that removes the per-session edit, and it is what
the TRANSITION_PROMPT recommended ("A first. B in Phase 3").

### Why the UUID, not the name, lives in `config.yml`

The tunnel has a human-readable name, `teachmewrite-django`. On 2026-11-22,
`cloudflared tunnel route dns teachmewrite-api api.teachmewrite.com` failed
with `teachmewrite-api is neither the ID nor the name of any of your tunnels`,
and `cloudflared tunnel rename teachmewrite-django teachmewrite-api` printed
`You did not specify any valid additional argument to the cloudflared tunnel
command.` The name is presentational. The UUID is authoritative. Both
`config.yml` and every `cloudflared tunnel ...` invocation use the UUID.

### Why `ALLOWED_HOSTS` keeps `.trycloudflare.com`

This is counterintuitive: we are moving **off** trycloudflare for the Cloud Run
callback, so why keep `.trycloudflare.com` in `ALLOWED_HOSTS`?

Because the **Vite tunnel** -- the browser-facing one -- is still a quick
tunnel. When the browser at `<vite-tunnel>.trycloudflare.com` sends a request to
the Django API, Vite's preview proxy forwards the request with
`Host: <vite-tunnel>.trycloudflare.com` to Django on `127.0.0.1:8000`. Without
`.trycloudflare.com` in `ALLOWED_HOSTS`, that browser session fails with
`DisallowedHost` before it ever exercises the named tunnel. The named tunnel is
used for the **Cloud Run callback path**, not for the browser session. Both
hostnames must be in `ALLOWED_HOSTS` because both paths exist.

Day 112 (or later) is the day the Vite tunnel is also named; on that day
`.trycloudflare.com` can come out of `ALLOWED_HOSTS`.

### The origin-liveness constraint

The named tunnel's address is stable, but the origin behind it is not. When the
Colab runtime recycles, `runserver` and `cloudflared` die, and
`api.teachmewrite.com` starts returning **HTTP 502** from Cloudflare's edge.
Cloudflare's 502 is the documented signature of a healthy tunnel whose origin
is not answering. The golden-set gate in `deploy.yml` calls the ai-service
synchronously; if the ai-service's `BackgroundTask` target (Django) is dead, the
gate fails closed. That is the pipeline behaving correctly, and it is the
constraint Day 111 exposed.

## 4. The Debugging Diary

### Entry 1 -- Colab Secrets are not exported to `os.environ`

Cell 3's first run failed at `assert gh, "GITHUB_TOKEN not set in Colab env"`.
The Colab Secrets panel showed `GITHUB_TOKEN` and `ANTHROPIC_API_KEY` present
and toggled on for the notebook, but `os.environ.get('GITHUB_TOKEN')` returned
`None`.

Cause: Colab Secrets live behind `google.colab.userdata.get(name)`. They are
not exported to `os.environ`. The Day 110 resume pattern used `os.environ`
throughout; on a fresh session with only Colab Secrets, every `os.environ`-based
check fails silently until something downstream notices.

Fix: Cell 3-FIX reads via `userdata.get(...)`, asserts prefix and length (not
the value), and prints prefix only. Cell 3-SHIM exports both values to
`os.environ` for the remainder of the session, so `git` and subprocesses see
them. Every cell that needs a token now works unchanged after the shim.

Lesson: **Colab Secrets are `userdata.get`, not `os.environ`.** The shim is the
smallest fix and it is durable for the session. Add to the resume pattern.

### Entry 2 -- Cloudflare error 1010 (Browser Integrity Check)

Cell 6's first run failed at the `/api/v1/users/me/` probe: `expected 401,
got 403, body: error code: 1010`. The tunnel was healthy (Cell 5: three
connections registered). Django was healthy (Cell 4.8: local 401). The
403/1010 was coming from Cloudflare's edge, before the request reached
`cloudflared`.

Cause: Cloudflare's Browser Integrity Check flags non-browser User-Agents.
Python's `urllib` sends `Python-urllib/3.x` by default. Cloudflare's docs
describe 1010 as a UA-based signature rejection, and the recommended resolution
is to send a descriptive, application-specific UA; a browser UA is not required.

Fix: Cell 6-revised sets `User-Agent: teachmewrite-probe/1.0` on every probe.
Both endpoints then returned Django's own 401 JSON.

Because the ai-service's `save_progress_task` also posts to the same hostname,
Cell 6.5 read `ai-service/main.py` to confirm the client. It uses
`httpx.Client()` with no explicit UA override, so httpx sends
`python-httpx/0.x.y`, which is descriptive and passes BIC. **No ai-service
change is needed** for the callback path.

Lesson: **a 403 with a numeric body from Cloudflare is an edge decision, not a
Django decision.** Check the UA first. Any client that is not a browser and not
`requests`/`httpx` may need an explicit UA.

### Entry 3 -- Deploy `83e25e0` failed golden-set gate, 0/20, HTTP 502

After Cell 7's push of `83e25e0`, the Actions run triggered. The golden-set gate
ran 20 cases; all 20 returned `HTTP 502`. Exit code 1.

Cause: the Colab runtime had recycled between 2026-11-22's Cell 6 (when the
tunnel and Django were proven live) and the 2026-11-23 morning deploy. The
tunnel process and the runserver process both lived in that runtime. When the
runtime died, both died. `api.teachmewrite.com` then returned Cloudflare 502,
which is the documented signature of "tunnel is up, origin is not answering."
The golden-set harness calls the ai-service synchronously, which calls Django
via the BackgroundTask target; the dead origin produced 502 on every case.

Fix: **not a code change.** The `deploy.yml` URL is correct. The tunnel UUID
and DNS CNAME are correct. The credentials on Drive reconstruct the tunnel. The
fix is a **workflow constraint**: before pushing any commit that triggers
`deploy.yml`, the origin must be running and `api.teachmewrite.com` must answer
the two 401s from Cell 6. If the origin is not up, the gate correctly fails and
no broken deploy reaches production. That is the pipeline doing its job.

Day 112 opening: restart Colab, run Cells 2.5 through 6 (the full resume
sequence), confirm Cell 6 passes, then `workflow_dispatch` the `83e25e0` run.
No new commit is needed.

Lesson: **"pushed" is not "deployed."** A stable URL gives the pipeline a stable
target, and the pipeline will correctly fail when that target's origin is down.
The pre-push probe (Cell 6) is the gate that prevents this failure class from
recurring. Add to the resume pattern.

## 5. Key Takeaways

**5.1 -- A stable URL is a DNS-and-identity property, not a process property.**
The named tunnel gives `api.teachmewrite.com` a fixed target across sessions.
The origin (Colab runserver) remains ephemeral. Those are two different
stability questions, and Day 111 answers only the first.

**5.2 -- The UUID is authoritative; the name is presentational.**
`cloudflared tunnel route dns teachmewrite-api ...` failed because the tunnel
name was `teachmewrite-django`, and `tunnel rename` did not accept the syntax
we tried. The UUID `4cdfe145-...` worked first time. Pin the UUID everywhere --
`config.yml`, every `cloudflared` invocation, and any future docs. Never rely
on the name.

**5.3 -- Cloudflare 1010 is Browser Integrity Check, not a Django bug.**
A 403 with body `error code: 1010` on a probe that was supposed to be 401 is
an edge decision. The fix is a descriptive `User-Agent`, not a `deploy.yml`
edit and not a Django change. `requests`/`httpx` defaults pass; `urllib`
defaults fail.

**5.4 -- Colab Secrets are `userdata.get`, not `os.environ`.**
The Day 110 resume pattern assumed `os.environ`. On a fresh session that only
has Colab Secrets, `os.environ.get('GITHUB_TOKEN')` is `None` even when the
secret is present and toggled on. The shim (`os.environ[name] = userdata.get
(name)`) fixes it for the session.

**5.5 -- "Pushed" is not "deployed"; the pipeline gates on origin liveness.**
`83e25e0` is the correct commit. The 0/20 HTTP 502 is the pipeline correctly
refusing to promote a service whose callback target is dead. The fix is a
pre-push Cell 6 probe, not a code edit. This constraint belongs in the resume
pattern and in `README.md`'s Known Issues.
