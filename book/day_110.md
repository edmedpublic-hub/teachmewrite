## 2. The Architecture (Why)

### The two hops Cell 13 exposed

Cell 13 was designed to start a Django tunnel and verify it routes. Its
asserts accepted status codes in `(400, 401, 403, 404)` -- deliberately
permissive because I did not know which error to expect. Both endpoints
returned 400 with a 70KB HTML body. The assert passed. The tunnel was
"working."

The body was Django's DEBUG error page: `DisallowedHost`. Django's
`ALLOWED_HOSTS` (settings.py line 15-18) defaults to `localhost,127.0.0.1`.
The tunnel forwards `Host: vacations-second-sponsorship-tourism.trycloudflare.com`
and Django refuses the request before auth even runs.

A second failure hid behind the first: `backend/.env` is gitignored, so a
fresh clone has no `INTERNAL_API_KEY`. Even after `ALLOWED_HOSTS` is fixed,
`_check_internal_key()` would return `Service not configured`. But we could
not observe that until the first failure was resolved.

Cell 13-fix resolved both:

- Write `backend/.env` with `ALLOWED_HOSTS=localhost,127.0.0.1,.trycloudflare.com`
  and `INTERNAL_API_KEY=<same key as Secret Manager>`
- Restart Django `--noreload` (settings.py reads .env at process start)
- Verify three specific status codes, each mapping to a different layer:
  - 401 on `/essays` unauthenticated -> ALLOWED_HOSTS accepts the host
  - 401 on callback without key -> service auth working
  - 404 on callback with valid key + bad user -> business validation working

That is the correct shape of a status-code test: three codes, three layers,
each in its own namespace. The permissive assert in Cell 13 accepted any of
the codes from any of the layers, which is why it "passed" while the system
was broken.

### Why the tunnel, not loopback

The whole reason for a second cloudflared tunnel: Cloud Run and Colab are
on different networks. Cloud Run is in GCP. Colab is an ephemeral VM behind
Google's notebook infrastructure. There is no route from Cloud Run to
Colab's `:8000` except through a public URL.

Options were:

- **Tunnel (chosen for today):** second cloudflared for :8000. Free, no
  account, rotates URL per session. `DJANGO_API_URL` in `deploy.yml` must
  be updated every session -> a deploy every session.
- **Django on Cloud Run:** sustainable. Requires Dockerfile, migrations
  at startup, Postgres, prod settings, secrets management. Multi-hour
  build. Correct long-term answer, wrong answer for a single day.
- **Named cloudflared tunnel:** stable subdomain, no per-session redeploy.
  Requires Cloudflare account + a domain. One-time setup ~20 min. Right
  answer for tomorrow.

Today chose tunnel-for-single-session. The commit message names the cost
explicitly: "Per-session cost: this URL rotates when the tunnel restarts."

### Three-lens audit

**Seamless.** Yes. Student submits an essay, feedback persists, appears in
their essay list. The seam (background task firing after HTTP response) is
invisible to the user -- it either works within a few seconds or it does
not, and there is no user-visible intermediate state to confuse.

**Easy UX.** Yes at the feature level (submit -> see it in the list is
self-explanatory). No at the polish level: loading spinners, error copy,
empty-state illustration are all minimal. Phase 2 Days 112-114.

**Futuristic.** Yes. Each essay is tagged `tier_at_submission`. When the
student graduates BASIC -> INTERMEDIATE, their BASIC-era essays stay
tagged BASIC. Historical accuracy preserved per row. That is the
futuristic lens artifact the design predicted on Day 106.

### What this is NOT

- **Not production-grade persistence.** The Django tunnel is ephemeral.
  Tomorrow's session gets a different URL; `deploy.yml` will need editing.
  Day 111's fix: named tunnel or Django on Cloud Run.
- **Not the auto-unlock work.** `TierProgress.update_progress()` still
  does not flip `is_unlocked` on the next tier when a tier is completed.
  Day 106 finding 1, still open.
- **Not DB-verified.** The runtime recycled at end of session, wiping
  `/content/` including the SQLite file. The row that produced the browser
  `/essays` page existed on disk when the page was fetched; it is gone
  with the session. The browser paste is the evidence. That is honest,
  not ideal.

## 4. The Debugging Diary (Exact errors and fixes)

**Three entries. Two system findings. One process finding. None cost a
deploy cycle because every failure was caught before deploy.**

### Entry 1 -- permissive assert hid the actual status code

Cell 13 checked reachability with `assert r.status_code in (200, 400, 401, 403, 404)`.
Both endpoints returned 400. Both asserts passed. The tunnel was "working."

The 400 was Django's `DisallowedHost` -- the tunnel forwards a Host header
Django has not been told to accept. `ALLOWED_HOSTS` default is
`localhost,127.0.0.1`. The tunnel hostname is
`vacations-second-sponsorship-tourism.trycloudflare.com`, not in the list.
Django refuses before auth runs.

Fix: `ALLOWED_HOSTS=localhost,127.0.0.1,.trycloudflare.com`. The leading
dot is wildcard for subdomains.

Lesson: **`assert in (a, b, c)` is not a test, it is a hope.** When you
do not know which code to expect, that is the signal you have not yet
understood the system. The fix is to understand the system, then assert
on the specific expected value.

### Entry 2 -- `.env` is gitignored; fresh clones have no INTERNAL_API_KEY

`backend/.env` was added to `.gitignore` on Day 107 (Cell 6b-1 step 1).
That is correct -- secrets belong in Secret Manager, not git. But the
consequence is that a fresh Colab session has no `INTERNAL_API_KEY` in
Django's environment, so `_check_internal_key()` would return
`Service not configured` on every callback.

For seven sessions (Days 105-109), this did not matter because Django
was tested from Colab directly (127.0.0.1:8000) and the callback was
local-only. The moment the callback became reachable from Cloud Run
(Day 110's second tunnel), the missing `.env` became a live failure.

Fix: Cell 13-fix writes `backend/.env` from the Drive backup of the key
(fingerprint `2c4be7f1`). The Drive backup exists precisely because of
this kind of scenario -- Day 108's decision to persist the key to Drive
paid off today.

Lesson: **gitignored secrets do not arrive in a fresh clone. The resume
pattern must include a cell that writes `.env` before any endpoint that
needs it is tested.** Day 111's Cell 5 must write `.env` before starting
Django, or explicitly document that the next cell will.

### Entry 3 -- runtime recycled mid-session; DB row unrecoverable

At the end of Day 110's primary work, Colab recycled the runtime while
I was about to run Cell 16b (DB verification of the row the browser had
shown). `/content/teachmewrite` no longer existed. The DB row that
produced the `/essays` page existed on disk at the moment of fetching;
it was destroyed with the session.

The browser paste is the evidence. `1 essay submitted, 42/100,
PROFESSIONAL` is what the user saw. That page was rendered from a
`WritingFeedback` row that had been created by the Cloud Run background
task, not by anything in the browser cache. Nothing can retroactively
unmake that.

Fix: re-clone (Cell 17) and continue the wrap. The row is gone; the
milestone stands. Day 111 first action, if DB verification matters:
re-submit an essay and immediately verify before the runtime can recycle.

Lesson: **browser evidence and DB evidence are independent.** The DB
evidence is stronger (it shows the exact row with field-by-field values).
The browser evidence is sufficient (it proves a row was created and
returned). When the runtime recycles, accept the loss of the stronger
evidence and move on. Do not chase proof that is gone.

## 5. Key Takeaways

**5.1 -- The loop is closed.** Three-pillar architecture (auth, AI, persistence)
working in production, end-to-end, in one user action. Days 107 (local proof),
108 (deploy failed), 109 (deploy succeeded, loopback), 110 (tunnel + URL).
Four consecutive days to close one loop -- but the loop is closed and the
browser evidence is the strongest proof we have had of any deliverable so far.

**5.2 -- Permissive asserts are hope dressed as verification.**
`assert status in (200, 400, 401, 403, 404)` accepted 400 (DisallowedHost)
as success. The fix was not "add 400 to the permitted set" -- it was to
understand what 400 meant, fix the cause, and then assert on the specific
code that would appear if the fix worked (401). When you do not know which
error to expect, that is the signal you have not yet understood the system.
Understand first, assert second.

**5.3 -- Infrastructure layers hide each other.** Two failures stacked in
Cell 13: `ALLOWED_HOSTS` (Django rejecting the tunnel hostname before auth)
and missing `INTERNAL_API_KEY` (would fail `_check_internal_key` even if
hostname were accepted). The second was invisible until the first was fixed.
This is the correct shape of infrastructure debugging: expect that one
failure masks another, and after each fix, ask "what is the next layer?".

**5.4 -- The Drive backup paid off.** Day 108's decision to write
`INTERNAL_API_KEY` to `/content/drive/MyDrive/teachmewrite-ai/.secrets/`
was made when the key was ephemeral-only and had been pasted into chat
once (compromised). Today, when the runtime recycled and `.env` was gone,
the Drive backup restored the exact key (fingerprint `2c4be7f1` verified)
without any regeneration or re-rotation. **The persistence discipline
established two days ago was exercised for the first time today.**

**5.5 -- Browser evidence and DB evidence are independent.** The DB row
proving the browser's `/essays` page was destroyed by the runtime
recycle. The browser paste is still the evidence that the row existed and
was returned correctly. **The browser paste is sufficient.** It is not
the strongest evidence (row-level DB verification would be), but it is
sufficient, and chasing gone proof wastes time. Day 111 first action if
stronger evidence matters: re-submit and immediately verify.

**5.6 -- One-line change, four-layer test.** The commit `ad575f3` is one
line in `deploy.yml`. The verification behind it was four tests: three
status codes against three layers of the Django callback, plus a full
browser E2E. **The size of the change is not a proxy for the size of the
test surface.** Any production URL change deserves the same four-layer
verification regardless of how few characters changed.

**5.7 -- What remains for Day 111.** Ranked:

1. **Named cloudflared tunnel or Django on Cloud Run.** The tunnel URL is
   ephemeral -- it changes every session. `deploy.yml` must be edited every
   session. Named tunnel: ~20 min setup, stable subdomain, done. Django
   on Cloud Run: multi-hour, sustainable, correct long-term.
2. **`TierProgress.update_progress()` auto-unlock.** Day 106 finding 1.
   15 lines + a test. A student who masters all BASIC lessons graduates
   to INTERMEDIATE without manual intervention.
3. **`fastapi.log` append mode.** Day 107 defect. One-line fix.
4. **Resume pattern must write `.env` before starting Django.** New finding
   from today. Add to Cell 5 or a new Cell 4.5.
5. **UI polish for My Essays.** Loading spinner, error copy, empty-state
   illustration. Phase 2 Days 112-114.
6. **Capture browser E2E screenshots.** Day 109 and Day 110 both have
   browser evidence only in chat transcript. A screenshot saved to Drive
   would survive even runtime recycle.
