## 2. The Architecture (Why)

### Three-lens audit applied before code

Before writing any Pillar 3 code, four decisions were audited against the three
lenses established Day 106:

1. **Seamless functionality** -- the user should never hit a seam where the
   system forgets them.
2. **Easy UX** -- the interface should tell the truth about the user.
3. **Futuristic** -- the system should cater to how users evolve over time.

Each decision was tested against all three lenses. Two decisions had lens
conflicts that were honestly named, not hidden.

### Decision 1 -- Local-first or deploy-first

**A. Local-first:** build, prove on Colab, deploy Day 108.
**B. Deploy-first:** build, deploy, verify in browser.

Lens audit:
- Seamless: both prove persistence. A proves it once; B proves it every deploy.
- Easy UX: **A ends today with no visible change.** This is honest cost.
  Persistence is silent. The user will not see their essay history until
  Day 108's "My Essays" UI. B also does not deliver visible change today
  because "My Essays" does not exist. Lens tied at zero.
- Futuristic: A produces a documented seam. B produces a deployed seam whose
  reachability from Cloud Run to Colab is an unsolved per-session problem.

**Verdict: A.** Cost was named: no user-visible deliverable today. Compensated
by Day 108 including the visible UI.

### Decision 2 -- Callback auth model

**(i) X-Internal-Key** -- service-to-service shared secret.
**(ii) Captured JWT** -- pass user's JWT to background task; Django verifies.

Lens audit:
- Seamless: (i) fail-closes on missing key; (ii) fail-opens if JWT expires
  between request and background task (rare, but a seam).
- Easy UX: no impact.
- Futuristic: (i) survives queue workers (Phase 3), (ii) does not.

**Verdict: (i).** Requires `INTERNAL_API_KEY` env var. In Cloud Run deployment,
must migrate to Secret Manager (Day 108).

### Decision 3 -- Idempotency key source

FastAPI's `request.state.request_id` (uuid4.hex set by middleware) vs a
new FastAPI-side session_id.

Lens audit:
- Seamless: request_id is already unique per HTTP request, zero new code.
- Easy UX: no impact.
- Futuristic: request_id survives retries and background re-fires.

**Verdict: request_id.** Zero new code on FastAPI side. Passed to
`save_progress_task` as `session_id` param. Django uses `get_or_create(session_id)`.

### Decision 4 -- tier_at_submission computation

(a) Inline query in callback view.
(b) `TierProgress.current_tier_for(user)` classmethod.
(c) Skip field today.

Lens audit:
- Seamless: (b) centralizes so all consumers agree. (a) duplicates logic that
  could drift.
- Easy UX: enables Day 108+ "My Essays" to show consistent tier per entry.
- Futuristic: **the field is the futuristic artifact.** Historical feedback
  must remember the tier it was given at, even after graduation.

**Verdict: (b).** Closes Day 106 finding 5 (duplicate tier-compute).

### The WritingFeedback schema

New model in `lessons/models.py`:

    class WritingFeedback(models.Model):
        user = ForeignKey(User, related_name='writing_feedback')
        session_id = UUIDField(unique=True)         # idempotency
        student_text = TextField()                  # student's own writing
        level = IntegerField(1-7)                   # essay grade parameter
        tier_at_submission = CharField(Tier.choices)  # historical tier
        overall_score = IntegerField(0-100)
        issues = JSONField(list)
        rewrite_suggestion = TextField()
        level_appropriate = BooleanField()
        created_at = DateTimeField(auto_now_add)

**Three schema choices with intent:**

1. **`session_id UNIQUE`** -- database-enforced idempotency. Duplicate POSTs
   cannot create duplicate rows. This is a schema-level guarantee, not a
   code-level promise.
2. **`tier_at_submission`** -- the futuristic lens artifact. A student's
   BASIC-era essay stays tagged BASIC even after graduation to
   INTERMEDIATE. Teachers later can chart progression by tier cohort.
3. **`student_text` stored but never logged** -- the callback's docstring
   names this rule. Day 105's httpbin incident was the violation of this
   rule; the fix is not to encrypt the log but to never send the text where
   logs could reach it.

### What this work is NOT

- **Not deployed with a working callback.** Cloud Run runs the new code but
  fail-closes on POST because `INTERNAL_API_KEY` is not in `deploy.yml`.
  Correct state. Day 108 migrates to Secret Manager.
- **Not user-visible.** No "My Essays" page. Persistence is silent. Day 108
  adds visibility.
- **Not the tier-evolution rule.** `update_progress()` still does not flip
  `is_unlocked` on the next tier when a tier is completed. Separate Day 108+.

## 4. The Debugging Diary (Exact errors and fixes)

**Five entries, all test-harness. Zero system bugs. This is the day's
dominant pattern.**

**Entry 1 -- sqlite3 vs Django UUIDField on SQLite**

- Cell 6b-2 T2 failed: HTTP returned `200 {"created": false, "id": 1}` --
  callback correctly detected the duplicate -- but `assert n == 1` on
  count query returned 0.
- Cause: Django stores `UUIDField` on SQLite as 32-char hex (no hyphens).
  My query passed `str(uuid.uuid4())` (36-char hyphenated). SQLite string
  equality: 32 != 36, zero matches.
- Fix: `_count_for_session(session_uuid)` helper uses `session_uuid.hex`
  (32 chars). Re-ran as Cell 6b-3. All 5 tests pass.
- Lesson: **Raw sqlite3 queries bypass ORM type conversion.** Verify
  UUIDFields via ORM, not via raw SQL, unless you replicate the conversion.

**Entry 2 -- for-loop on one line with semicolons**

- Cell 8b failed: `SyntaxError: invalid syntax` at `for r in rows:    print(...)`.
- Cause: compressed a for-loop onto one line with `;` separators inside a
  shell string. Python does not allow compound statements after `;`.
- Fix: multi-line triple-quoted shell string; `%`-formatting instead of
  f-strings (nested f-string braces would be ambiguous).
- Lesson: **when the outer cell uses f-strings, use `%` or `.format()` in
  the inner shell string.** Two formatting layers, two styles.

**Entry 3 -- variable assignment instead of assertion**

- Cell 8 wrote `pre_count = 0` (a variable assignment) after the shell had
  correctly reported `[db] pre count: 1`. The cell passed despite finding an
  unexpected row.
- Cause: I wrote a comment describing intent instead of an assert enforcing it.
- Consequence: Cell 8 created a second row (id=4) without flagging the
  pre-existing first row (id=3). Caught by Cell 8b-2 audit, traced by Cell 8c
  log analysis. No data was harmed, but the finding was muted by a test that
  looked like it checked.
- Lesson: **if you write "expect X" in a comment, write `assert X == value`
  on the next line.** Comments do not fail; asserts do.

**Entry 4 -- expected-files list from memory**

- Cell 9 committed 5 files. Cell 9c discovered the working tree had 6
  modified files -- `auth_views.py` was omitted from Cell 9's expected list.
  The staged-vs-expected assert passed because both sides omitted the file.
- Cause: Cell 9's `files = [...]` list was written from memory of today's
  edits, not derived from `git status`.
- Fix: Cell 9c committed the missing file. Total commits: `9cbfd0e` (5 files)
  + `742b873` (1 file).
- Lesson: **derive expected-files list from `git status --porcelain`, not
  from memory.** `assert set(staged) == set(modified)` is not enough if both
  sets come from the same wrong memory.

**Entry 5 -- SHA slice width mismatch**

- Cell 9b failed: `assert run_9cb is not None` -- No workflow run found
  for 9cbfd0e. But the run existed in the API response.
- Cause: `r["head_sha"][:8] == "9cbfd0e"` compares 8 chars to 7 chars.
  `--short` produced 7-char SHAs; my slice assumed 8.
- Fix: Cell 9b-2 uses `.startswith(short_sha)`. Same pattern Day 105 used.
  Diagnose-first design listed all 10 recent runs before matching, so even
  if the match had failed again, we would see the run in the diagnostic.
- Lesson: **never slice a SHA. `.startswith()` is the only safe comparison.**
  `--short` width varies with collision risk (Git uses shortest unique
  prefix, minimum 7).

## 5. Key Takeaways

**5.1 -- Three-lens audit is a design tool, not a retrospective.** Before
Pillar 3 code, four decisions were audited (local-first, X-Internal-Key,
request_id, tier_at_submission via classmethod). Each had lens trade-offs
named explicitly. The one visible cost -- no user-visible change today --
was recorded before code, not discovered after. A design decision whose
costs are invisible is a decision whose costs will surprise you later.

**5.2 -- Test-harness discipline is the engineering priority now.** Five
test-harness bugs vs zero system bugs. Every single system in Pillar 3
(callback, idempotency, auth, tier compute, E2E persistence) worked
correctly on first real execution. Every failure was in the code written
to verify it. This is not a coincidence -- it is a signal. Verification
code needs the same discipline as system code:

  1. Shell strings: `compile(src, "<shell>", "exec")` before running.
  2. sqlite3 queries: prefer ORM; if raw, replicate type conversions.
  3. Expected values: derive from `git status` / ORM / API responses,
     never from memory.
  4. SHA comparisons: `.startswith(short_sha)`, never slice.
  5. Assertions: every "expect X" comment becomes `assert X == value`.

**5.3 -- Centralization closes duplicate-logic bugs at the source.** Day
106's alphabet-order bug happened because two code paths computed the
same thing (inline loop vs array serializer). Day 107's
`TierProgress.current_tier_for(user)` means future consumers (callback,
dashboards, teacher reports) share one source of truth. The next time an
alphabet trap is possible, it is possible in one place, not many.

**5.4 -- `tier_at_submission` is the futuristic artifact.** A historical
feedback row that remembers the tier it was given at is what makes
progression visible. Without it, a student who graduates from BASIC to
INTERMEDIATE and asks how did I write at BASIC has no answer -- the
history would show current tier, not historical tier. The field is small;
its consequence is not.

**5.5 -- Fail-closed is the right state for Cloud Run today.**
`INTERNAL_API_KEY` is not in `deploy.yml` yet. The deployed callback
rejects every background POST. This is honest: no silent writes, no
phantom progress, no path where student_text could go somewhere unexpected
if a config error occurred. Day 108 migrates the key to Secret Manager
and completes the deployment. The gap is planned, not accidental.

**5.6 -- The user-visible deliverable is deferred to Day 108, and that is
the honest cost.** Pillar 3 works. The user cannot see it working. "My
Essays" UI is Day 108. A future reader of this chapter should note: the
reason there is no screenshot of a persisted essay is that the UI for it
was not built yet. Persistence proven; visibility deferred. Not an
oversight, a sequencing choice.
