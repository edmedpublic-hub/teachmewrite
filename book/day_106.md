## 2. The Architecture (Why)

### What the inspection revealed

I began Day 106 expecting to design a tier model. The inspection cell (`21a-inspect`)
showed one already exists -- and it is better than what I would have designed:

- **`TierProgress`** (models.py 450-521): one row per `(user, tier)`, created by
  `initialize_user_tiers(user)`.
- **`is_unlocked: BooleanField`** -- gatekeeper for tier access; only `BASIC` unlocked on init.
- **`is_completed` + `completed_at`** -- the graduation signal.
- **`update_progress()`** -- recalculates from `StudentProgress` on mastery.

The model **already satisfies the futuristic lens**. Tier is changeable state (`is_unlocked`
flips as the student progresses), not a static label. My fear that we need to design a
changeable-tier model was misplaced -- it had been designed. What was missing was
*exposure*: the data existed, the API and UI did not read it.

**Lesson: inspect before designing. The correct design may be the one already in the repo.**

### Four decisions that shaped the work

**Decision 1 -- Where does current tier live?** Not `User.tier` (static). Not
`Profile.target_tier` (that is aspirational tier, a different concept). Computed:
`current_tier = highest tier with TierProgress.is_unlocked=True` for this user.
Explicit tier order `[PROFESSIONAL, ADVANCED, INTERMEDIATE, BASIC]`, not alphabetical.

**Decision 2 -- Who computes it?** Backend `UserViewSet.me` action. Returns computed
`current_tier` plus raw `tier_progress` array. Not the frontend -- tier semantics belong
on the backend where `Tier` enum lives.

**Decision 3 -- Does AuthContext fetch, or does Navbar fetch?** `AuthContext`. Navbar
renders in `ProtectedLayout` before child pages load -- it needs the user object already,
not in flight. Centralizing in AuthContext also serves Dashboard, Profile, MasteryReport.

**Decision 4 -- What happens when /me/ returns 401 (expired session)?** Catch it, clear
localStorage, set user to null. Graceful degradation, not a bug. But: **resilience hides
bugs**. Today's cell showed this -- a 404 fell into the same catch and silently cached
BASIC. Day 107: distinguish 401 (clear + redirect) from 404/500 (log loudly) from shape
errors (assert in dev mode).

### What this work is NOT

- **Not Pillar 3.** FastAPI BackgroundTasks still POST to `http://127.0.0.1:1/disabled`.
  No progress persists after `/feedback`. Pillar 3 is Day 107.
- **Not deployed.** Pipeline paths filter is `ai-service/**` only. `e3adc1a` lives on
  Colab. Travels to prod when Django deploys to Cloud Run (Days 108-110).
- **Not demo-user auto-creation.** `Cell 21a-users` patches demo accounts each session.
  Day 107: extend `seed_learning_data.py` or registration flow so real users get
  `TierProgress.initialize_user_tiers()` automatically.

## 3. The Implementation (How)

### Two files changed, one commit

**`backend/api/views/auth_views.py`** (+~40 lines):

- Added `Tier` to the `lessons.models` import
- Added `from django.db import models` for `Case/When`
- Added `@action(detail=False, methods=['get'], url_path='me')` to `UserViewSet`:
  - Computes `current_tier` = highest tier with `is_unlocked=True`
  - Returns `tier_progress` array in semantic order via `models.Case/When`
    (BASIC=0, INTERMEDIATE=1, ADVANCED=2, PROFESSIONAL=3, default=99)

**`frontend/src/contexts/AuthContext.jsx`** (91 lines -> 120 lines):

- Removed: `localStorage.setItem('user_tier', 'BASIC')` and hardcoded fallbacks
- Added `_cacheUser(u)` helper -- caches username + current_tier to localStorage,
  sets React state with a `tier` alias for Navbar compatibility
- Added `_fetchCurrentUser()` -- calls `authAPI.getCurrentUser()`, catches 401 by
  clearing localStorage, caches on success
- `checkAuth` optimistically renders cached data, then awaits `_fetchCurrentUser()`
- `login` calls `authAPI.login()` then `_fetchCurrentUser()`, returns enriched user
- `updateProfile` left as mock (separate Day 107 item)

### What I preserved, per Rule Zero

- `login` return shape `{ success, user, error }` unchanged
- `logout` behavior unchanged
- `isAuthenticated` reads localStorage unchanged
- `updateProfile` unchanged (still mock)
- Navbar's `user?.tier || 'BASIC'` read unchanged -- we now populate `user.tier` with real data
- `api.js` untouched -- `getCurrentUser` already existed, calling `/v1/users/me/`,
  waiting for an endpoint that did not exist. Now it exists.

## 4. The Debugging Diary (Exact errors and fixes)

**Entry 1 -- Cell 1 syntax error (own bug)**
- Cell 1's final `print()` was missing a closing `)`. Cell never ran. User fixed.
- Lesson: cells with a DONE sentinel must be `ast.parse`-verified before delivery,
  because a syntax error in the final line prevents the cell from running, so no
  assert can catch it.

**Entry 2 -- `npm install` risk (did not fire today)**
- Cell 20 expects `dist/` and `vite` binary; both require `npm install` first.
  Day 105 lesson learned. Day 106 did it right (Cell 20b before Cell 20). No failure
  this time -- but the resume checklist must always include Cell 20b.

**Entry 3 -- `git commit` exit 128 (author identity)**
- Day 105 set `git config user.email/user.name` -- but that is repo-local. Today's
  fresh clone had none. Cell 22b-commit set identity idempotently before committing.
- Lesson: any commit-carrying cell must set identity before `git commit`.

**Entry 4 -- Django `--noreload` and the 404 that disguised itself**
- After Cell 21a-navbar-backend edited `auth_views.py` (adding `me` action) and
  `ast.parse`-verified it, the running Django returned **404** to `/api/v1/users/me/`.
  Cause: `--noreload` means Django does not watch files; running process still held
  the old `UserViewSet` in memory. File edit succeeded; process state was stale.
- Fixed by `Cell 21a-navbar-django-restart` (kill + restart).
- Lesson: `--noreload` cells that edit Python must be followed by a restart cell.
  Verify port open is not enough -- verify endpoint returns 200 with real data.

**Entry 5 -- The alphabet trap I warned against in the same cell**
- In Cell 21a-navbar-backend, I wrote a comment: `order_by('-tier')` sorts
  alphabetically and would give wrong order. Then on the next line I wrote
  `.order_by('tier')` -- same trap, opposite direction. The compute loop used the
  explicit order list (correct); the array serializer used `.order_by('tier')` (wrong).
- Result: `current_tier` right, `tier_progress` array = `[ADVANCED, BASIC, INTERMEDIATE, PROFESSIONAL]`
  -- alphabetical. Latent; Navbar showed right, but any consumer of `tier_progress`
  would render wrong.
- Fixed by `Cell 21a-navbar-order-fix`: replaced with `models.Case(models.When(...))`.
- Lesson: when a data structure has a semantic order that is not natural sort, encode
  the order in the response-building code, not in an `.order_by()` clause. `.order_by()`
  is for database queries; semantic order in JSON is a business rule.

**Entry 6 -- Resilience hides bugs**
- `_fetchCurrentUser` catches all errors (network, 401, 404, 500) and returns null.
  When `/me/` returned 404 from the stale Django process, the catch fired silently and
  cached `current_tier: 'BASIC'`. Frontend looked healthy; Navbar showed BASIC; actual
  backend was broken.
- Not fixed today (this is the code we *want* -- graceful degradation on real outages).
  Logged: Day 107 should distinguish 401, 404/500, and shape errors.

## 5. Key Takeaways

**5.1 -- The design you need may already be in the repo.** I planned to design a
changeable-tier model. `TierProgress` had been designed -- with `is_unlocked`,
`is_completed`, `update_progress()`. Rule Zero applies to design, not just code:
inspect before you invent.

**5.2 -- The futuristic lens is a data question, not a UI question.** A user-facing
PROFESSIONAL badge is a *rendering*. The question is whether the system knows where
the user actually is, and can that change. Answer now lives in `TierProgress`, exposed
via `/me/`. The badge is a symptom; the state is the cure.

**5.3 -- `--noreload` is a discipline, not a convenience.** Colab needs it to avoid
fork/exec. But every Python-file edit needs a restart. From Day 107, Cell 7 must be
followed by a `--noreload restart` cell whenever any backend Python changes. Or:
Cell 7 becomes boot + verify endpoint responds with expected data, endpoint-specific,
not just port-specific.

**5.4 -- Alphabetical sort is the default trap, and I fell in it twice.** First time
in `current_tier` computation (avoided). Second time in `tier_progress` array building
(not avoided). The lesson is not remember to sort explicitly -- it is encode semantic
order as data, not as a sort key. `models.Case/When` says *this is a business rule*.
`.order_by('tier')` says *I trust alphabetical coincidence*.

**5.5 -- Five findings for Day 107:**

1. **Auto-unlock on tier completion missing.** `update_progress()` sets `is_completed`
   but never flips `is_unlocked` on the next tier. A student who masters all BASIC
   lessons stays locked out of INTERMEDIATE. Futuristic lens failing at the exact
   moment it matters.
2. **`/feedback` does not consume tier.** `FeedbackRequest` has `student_text` + `level`
   only. A `student_css` essay gets the same level-5 prompt as a `student_basic` essay.
   The `tier` field must be added (design recorded: `tier` in request,
   `tier_at_submission` in new `WritingFeedback` model).
3. **`updateProfile` is mocked.** Real `/users/profile/` endpoint exists; frontend
   does not call it.
4. **Dashboard shows 0/5 for all tiers** even when `student_css` has all four tiers
   unlocked. Two sub-findings: (a) `tier_progress` is now correct in `/me/`, so the
   Dashboard simply needs to consume it; (b) the Dashboard shows 7-day streak, 56 min
   practice, and recent activity on a fresh DB -- the source of that data is unknown
   and must be investigated before it can be trusted.
5. **Tier-compute logic is inline in `UserViewSet.me`.** A
   `TierProgress.current_tier_for(user)` classmethod would centralize it. Day 107 work
   will add more consumers.

**5.6 -- The chapter's length is a signal.** Day 105's chapter was 178 lines. Today's
is ~260. Not because more happened -- because more was *found*. The inspection phase
was as productive as the implementation phase. That is the correct ratio for a project
where the models are mature but the presentation is not. Phase 2 is not building.
Phase 2 is waking up what was already built.
